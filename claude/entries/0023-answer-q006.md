## Decisions I made
- **D-019's existing fidelity test had to change — disclosed per PROCESS_BRIEF §6.1 trigger 5,
  authorized by D-025 itself.** The original test committed a document already holding
  `NaN`/`+Infinity`/`-Infinity` literals and asserted ACCEPTANCE — exactly the fixture D-025 makes
  illegal. Split it: the fidelity claim for what remains legal (`null`, `Point`, `Point[]`,
  `ErrorValue`) is still demonstrated via an accepted, unrelated mutation; the non-finite members
  moved to the new D-025 describe block, now asserting REJECTION instead.
- **`findNonFiniteSlotValues` reuses `describeUndeclaredSlot` rather than reconstructing a path from
  a slot key.** My first draft wrote `key.split(".")` to build an `Address` for `formatAddress` —
  exactly the "invert `slotKey`" pattern D-010/D-022/STATUS's own gotchas rule out, caught before
  running any test. A literal slot's key need not correspond to any schema-declared path at all
  (extra literal slots are legal), so this check cannot assume the schema route check 2 uses; reusing
  the already-approved `describeUndeclaredSlot` (D-022's bounded exception) is a second CALL SITE,
  not a second raw-key-naming implementation, which is what D-022 actually forbids.
- **The finiteness check runs LAST in `validateIntegrity`, checking `literal`, `formula`, and
  `derived` slots uniformly (no schema-based exemption).** Value legality doesn't depend on schema
  structure the way D-017/D-018 do, so there's no ordering hazard to reason about — it was simply
  appended after the existing three.
- **Caught and corrected a real overclaim before finalizing (see Verification below for the
  mutation-test that surfaced it): `validateIntegrity` does NOT act as a backstop for a
  freshly-computed non-finite `derived` value.** It runs BEFORE `evaluate` in the mutation loop
  (`deriveEdges` → `validateIntegrity` → `detectCycle` → `evaluate`), and `evaluate`'s result is
  returned as-is, never re-validated. My first drafts of three separate comments (in
  `mutation.ts`'s check-4 description, `schema.ts`'s `add`-schema doc comment, and this cycle's own
  `mutate`-level test) all claimed `validateIntegrity` would "catch" an overflow that slipped past
  `add`'s own guard — false, and disproven directly by mutation-testing `add`'s guard (see below):
  removing it makes `mutate` return `ok: true` holding a raw `Infinity`. All three comments corrected
  in place before commit, rather than left standing. Same failure shape as 0018-REVIEW-phase0's
  finding 1 (a plausible doc-comment claim) and 0020's self-caught test-comment overclaim — caught
  here by the same discipline, one layer earlier (before even a mutation-test run showed it, the
  test outcome is what showed it, so really: caught BY running the mutation-test I'd have run
  anyway for load-bearing-ness, which is D-016's OWN "ask both questions" lesson working exactly as
  intended).

### D-016 mutation checks — four, one per new mechanism (plus the correctness-link discovery)
Each experiment: neutralize exactly one mechanism, confirm the specific test(s) that depend on it
fail and nothing else does, revert, confirm 169/169 again. All four reverted; confirmed via
`grep -rn "MUTATION-TEST" src/engine/` → no matches.

1. **`hasNonFiniteNumber`'s bare-number branch** (forced to always `return false`): exactly 4 tests
   failed — its own unit test, and the 3 `mutation.test.ts` D-025 tests that exercise a BARE
   non-finite literal (freshly-written, already-present-elsewhere, and the D-019-correctness-link
   test). The Point-nesting test and both `add`-overflow tests stayed green — precise.
2. **`hasNonFiniteNumber`'s Point/Point[] branches** (both forced to `return false`): exactly 3 tests
   failed — its own two Point/Point[] unit tests, and the one `mutation.test.ts` test asserting
   rejection of a non-finite number nested inside a `Point` literal.
3. **`validateIntegrity`'s check-4 wiring** (the `if` gated behind `if (false && ...)`): exactly 4
   tests failed — all four `mutation.test.ts` D-025 tests that go through `mutate`/`validateIntegrity`
   directly. The `add`-overflow test in the SAME describe block, and both `schema.test.ts` overflow
   tests, stayed green — they never touch `validateIntegrity` at all, confirming this check and
   `add`'s own guard are genuinely independent mechanisms, not one covering for the other.
4. **`add`'s own overflow guard** (gated behind `if (false && ...)`): exactly 2 tests failed —
   `schema.test.ts`'s new overflow test (`result` was a raw `Infinity`, not `{error:"#TYPE"}`), AND
   `mutation.test.ts`'s `add`-level accept/overflow test — `mutate`'s result was `ok: true` holding
   `{kind:"derived", value: Infinity}`. **This is the experiment that surfaced the overclaim**
   described in Decisions above: I expected (per my own first-draft comments) that removing this
   guard would still end in REJECTION via `validateIntegrity` "one step later" — instead the mutation
   was ACCEPTED with `Infinity` committed, proving `validateIntegrity` cannot and does not re-check
   `evaluate`'s own output. Three doc comments corrected in place (see Decisions) before this entry
   was written, not after.
