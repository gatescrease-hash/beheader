## Decisions I made
- **`findSchemaSlotKindMismatches` runs as its own function, not merged into
  `findUndeclaredFormulaOrDerivedSlots`.** D-017 and D-018 are separate rulings checking opposite
  directions of the same reconciliation; keeping them as two functions (called back-to-back) keeps
  each one's diff and blame history legible against the ruling that required it, at the cost of one
  extra function versus a merged loop. Both still run before the dangling-reference check, so the
  overall three-check order is unchanged from what the header already promised for D-017 alone.
- **The missing-derived-slot case and the wrong-kind-at-derived-path case share one check
  (`slot === undefined || slot.kind !== "derived"`)**, per D-018's own wording ("MUST carry a
  `derived`-kind slot" reads as one requirement, not two) — a single `if` with a two-branch message
  rather than two separate `if`s producing the same category of problem.
- **`mutate`'s D-021 check runs against the ORIGINAL `objects`, before `cloneObjects`.** Object
  identity (which ids exist) cannot change between "check" and "clone" — nothing between them reads
  or writes anything — so cloning first just to ask "does this id exist" would be wasted work with
  no correctness benefit. Rule 5 (dumbest correct implementation) doesn't ask for staging before a
  precondition check that doesn't need staged data.
- **D-021's rejection message names the target slot's PATH, never the `objectId`.** Considered
  `formatAddress` first, but it needs to resolve `objectId` to a name — impossible here by
  construction (that's the whole rejection) — so it would return its OWN `AddressError`, which
  itself states the raw id (`address.ts`'s `formatAddress`, not something this cycle touches).
  Following `findDanglingReferences`'s already-established stance (D-015: never leak a raw id) and
  naming only the path keeps this file's own messages consistent even though `address.ts`'s
  `formatAddress` doesn't hold itself to quite the same standard for its own failure case.
- **The D-019 fidelity test builds ONE object with several literal slots (one per `Value`
  variant), rather than one object per variant.** `validateIntegrity` doesn't restrict extra
  literal-kind slots against a schema (only `formula`/`derived`-kind slots are checked), so a single
  `value`-typed object with 7 additional literal slots is valid state and keeps the test's fixture
  short. The mutation itself targets a SEPARATE, second object — matching exactly the two-mutation,
  unrelated-target shape 0018-REVIEW-phase0's own probe used to demonstrate the original bug.
